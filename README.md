# PASTI IT Asset Register

Web version of **PASTI_Asset_Code_Registerv2.xlsx** — the IT Department's register of company devices,
who holds them, Electronic Device Pass badges, the security gate log, accessories and employee-owned
(BYOD) devices. Same codes, same rules, same accountability form — with real user accounts, an audit
trail, and nothing that can be silently overwritten or deleted.

**Stack:** React + TypeScript + Vite + Tailwind · Supabase (Postgres, Auth, Row Level Security) ·
Vercel (static site + one serverless function) · SheetJS for Excel · Recharts.
Design: the KLMS family (navy gradient sidebar, blue/teal, Inter), dark charcoal edition.

---

## 1. What it does

| Workbook sheet | Web page | Notes |
|---|---|---|
| Asset Register | **Asset Register** | Codes `PASTI-TYPE-YY-####` generated by the database; alerts as in the workbook |
| Assignment History | **Assignment History** + each asset's page | Rows are created by *Issue / Hand over / Return* — no macro needed |
| Device Pass Badge Register | **Gate Passes** | `PASTI-EDP-TYPE-YY-####`, 3-month validity, renew keeps the ID |
| Gate Movement Log | **Gate Log** | Live ALLOW / DO NOT ALLOW / CHECK WITH IT, verdict stored by the database |
| Employees | **Employees** | Devices/accessories/badges held, form status, exit clearance |
| Employee Summary | Employee page → **Print accountability form** | Same layout and wording, prints on A4 |
| Accessory Log | **Accessories** | |
| Employee-Owned Devices | **Personal Devices** | `PASTI-BYOD-TYPE-YY-####` |
| Type Codes, Lists | **Settings & Users** | Admin only |
| (new) | **Dashboard**, **Activity Log**, **Import from Excel** | |

### Roles (enforced by the database, not just hidden buttons)

| Role | Can |
|---|---|
| **Viewer** | Read everything, export to Excel, print forms |
| **Editor** | Viewer + register/edit assets, issue/return, badges, gate log, accessories, BYOD, employees |
| **Admin** | Editor + users & roles, lists, Excel import, delete records entered by mistake |
| *(no role)* | Can sign in but sees nothing until an admin approves them |

## 2. Local development

```bash
npm install
cp .env.example .env.local      # then fill in the values (see below)
npm run dev                      # http://localhost:5173
```

### Trying it without a Supabase project

`scripts/dev-backend.ts` is a **development-only** stand-in for Supabase: real Postgres (PGlite) running
the real migrations and RLS behind the small part of the Supabase API this app uses. In-memory; resets on
restart; listens on 127.0.0.1 only; never deployed.

```bash
# .env.local
VITE_SUPABASE_URL=http://localhost:54321
VITE_SUPABASE_ANON_KEY=dev-anon-key
```
```bash
npm run dev:backend    # terminal 1
npm run dev            # terminal 2
```
Sign in as `admin@pasti.local`, `editor@pasti.local` or `viewer@pasti.local` (password `dev-password`).

## 3. Deploying (GitHub → Vercel + Supabase)

### 3.1 Supabase
1. Create a project at supabase.com (region **Southeast Asia (Singapore)** is closest to the Philippines).
2. **SQL Editor** → run these files **in order**, each once:
   `supabase/migrations/0001_core.sql`, `0002_workflows.sql`, `0003_security.sql`, `0004_default_lists.sql`.
3. **Authentication → Sign In / Providers**: keep Email on, turn **off “Allow new users to sign up”**.
4. **Authentication → URL Configuration**:
   - Site URL: `https://<your-app>.vercel.app`
   - Redirect URLs: `https://<your-app>.vercel.app/set-password` and `http://localhost:5173/set-password`
5. Create the first administrator: **Authentication → Users → Add user** (email + password, *Auto Confirm*),
   then in the SQL Editor:
   ```sql
   update profiles set role = 'admin', full_name = 'Your Name' where email = 'you@company.com';
   ```
6. **Project Settings → API**: copy the Project URL, the `anon` key and the `service_role` key.

### 3.2 GitHub
Create an empty private repository (e.g. `hades9160/pasti-assets`) and push this folder.

### 3.3 Vercel
1. **Add New → Project** → import the repository. Framework preset: **Vite** (build `npm run build`, output `dist`).
2. **Environment Variables**:

   | Name | Value | Environments |
   |---|---|---|
   | `VITE_SUPABASE_URL` | Project URL | All |
   | `VITE_SUPABASE_ANON_KEY` | anon key | All |
   | `SUPABASE_URL` | Project URL | Production, Preview |
   | `SUPABASE_SERVICE_ROLE_KEY` | service_role key | Production, Preview — **never** with a `VITE_` prefix |

3. Deploy. `vercel.json` adds the SPA rewrite and security headers (CSP allows only this site, Supabase and Google Fonts).

### 3.4 First run
1. Sign in as the administrator.
2. **Import from Excel** → choose the workbook → check the preview → tick the box → **Import workbook**.
   This works once, on an empty register, and is all-or-nothing.
3. **Settings & Users → Invite user** for each colleague (they get an email to set a password).

### 3.5 Production checklist
- [ ] Viewer account cannot see Register/Issue buttons and gets an error if it tries via the API
- [ ] A new sign-up without a role sees “Waiting for approval”
- [ ] Register → Issue → Issue gate pass → Gate Log shows ALLOW
- [ ] Hand over → old pass shows DO NOT ALLOW
- [ ] Export to Excel opens in Excel; Print form fits one A4 page
- [ ] Invite user email arrives and the link opens `/set-password`
- [ ] Supabase **Database → Backups** are enabled for your plan

## 4. How the workbook rules were translated

All calculated columns live in `src/lib/rules.ts` (one function per column, each commented with the
column it replaces). The database enforces what must never break:

| Rule | Where |
|---|---|
| Asset/BYOD/Badge codes: per type, per year, 4-digit running number, never reused (voided codes stay used) | `code_counters` + triggers in `0001_core.sql` |
| Codes are fixed for life; device type / year cannot change afterwards | `assign_device_code()` |
| Same serial twice on the register (Void ignored) | unique index `assets_serial_key` |
| A unit is company-owned **or** employee-owned | `check_cross_register_serial()` |
| One current holder per asset; return date not before issue date | `assignments_one_open`, `assignments_dates` |
| One active badge per device; revoked badges never reactivate | `badges_one_active_*`, `guard_badge_status()` |
| Issue / hand-over / return update register + history + badges together | `issue_asset()`, `return_asset()` |
| Gate verdict computed by the database at logging time | `log_gate_movement()` → `gate_alert()` |
| Never delete assets, badges, history or gate log | RLS + revoked DELETE |
| Every change logged with who/when; deleted rows kept | `log_change()`, `deleted_records` |

### Decisions taken (please confirm)
1. **“Valid Until” on the Asset Register was dropped** (agreed): validity applies to gate passes only.
2. Duplicate serials and duplicate employee names are **blocked**, not just flagged red.
3. Returning an asset (or marking it Lost/Decommissioned/Void) **closes the history record, clears the holder
   and revokes its active pass** in one step — the workbook's Read Me steps 1–3. Handing over to someone else
   also revokes the previous holder's pass (the workbook's Check column asked for this).
4. **Under Repair** keeps the holder accountable (still counted in Devices Held), as in the workbook.
5. A gate pass can only be issued for an **Active** device that has a holder.
6. To fix a wrong device type or a date in the wrong year, **Void and re-encode** — the code cannot change.
7. The gate log stores the verdict *at the moment of logging*; the workbook recalculated old rows every day.
8. The printed form lists **all** items (the workbook showed at most 10 devices / 15 accessories / 5 BYOD).
9. “Today” is the calendar date in **Asia/Manila**.
10. New employees need a department (the workbook only warned).

### Open questions
- Employment statuses are fixed to *Active / On Leave / Resigned/Separated* because Exit Clearance depends on
  the exact wording. Are other statuses needed?
- The placeholder-serial rule copies the workbook exactly (`-00` anywhere, the word “monitor”, `1234567890`,
  or no digits). Real serials that contain `-00` will show a warning — keep or relax?
- Who should be Editor vs Admin in practice (IT staff, HR, Security)?

## 6. Known limitations
- The full-workbook import runs once; later bulk imports are employees only. Everything else is entered in the app.
- `.xls` (pre-2007) files are read by SheetJS but were not tested; save as `.xlsx` if a file is rejected.
- Invitations use Supabase's built-in email sender, which is rate-limited; configure SMTP in Supabase for
  more than a few invitations per hour.
- Tested end to end against the local stand-in, not yet against a real Supabase project — run the
  production checklist after deploying.
